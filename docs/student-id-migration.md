# 学号规范化与安全迁移方案

## 新规则与兼容性

统一实现位于 `packages/shared/src/student-id.ts`：仅接受4–24个ASCII英文字母或数字，校验原始文本后转为大写；不进行数字转换、不删除空格，不接受全角字符、换行、连字符等。前导零原样保留。登录、创建、编辑、Excel、bootstrap 使用同一规则。唯一映射键为 SHA-256(normalizeStudentId(studentId))；登录失败计数也以规范化后的学号归并。

纯数字旧账号的值及 SHA-256 映射键不变，无需迁移。旧版正式API本来拒绝字母学号，因此通过旧版API创建的档案可直接兼容。密码重置等管理路由使用稳定 UID，学号更正不改变 UID，回归测试覆盖该路径。

当前执行环境未配置 CloudBase 环境ID，**没有读取或修改生产数据库，不能断言实际数据库中不存在手工写入的字母学号**。下面是需要部署者在受控环境审查、实施的方案，不是已经执行的迁移，也不包含自动启动的迁移脚本。

## 何时需要迁移

若曾通过控制台、旧脚本或其他入口手工写入含小写字母的 `users.studentId`、旧 `student_ids` 映射或导入记录，必须先做只读审计并迁移，再开放新版创建/编辑/导入接口，防止旧的非规范映射被漏检。

## 不覆盖已有数据的执行流程

1. 备份 users、student_ids、sessions、login_limits、import_jobs、privacy_jobs、audit_logs 与 system/control；记录备份版本及恢复方法。进入维护窗口，暂停成员写入、登录与导入；迁移期间不要同时发布新旧写入实例。
2. 只读分页扫描全部 users（包含禁用、软删除账号；跳过已匿名化且学号为空的墓碑）。使用共享函数计算规范值；不符合新规则的记录只报告 UID，交由授权人员核实，不猜测修复或补零。
3. 按规范值分组。若多个 UID 归并到同一个学号，**停止整次迁移**并保留所有账号。不得以“先到先得”覆盖、合并或删除账号；由授权人员核实真实身份后另行处理。
4. 检查每个旧映射及规范映射。旧映射必须指向原 UID；规范键若已指向其他 UID、发现孤立映射或数据不一致，停止并人工调查。先生成只读计划，记录 UID、旧版本、旧键、新键；个人信息只留在受控报告中，不写 Git 或公共日志。
5. 审查计划后逐个用户执行小事务，共同读写 system/control 以与业务写入互斥。重新核对 UID、原 studentId、updatedAt、version 及映射归属；任何值与计划不一致立即回滚并停止。只有目标键不存在或已归属同一 UID 时，才写入规范映射。
6. 保留同一 UID；仅更新 users.studentId、updatedAt，并增加 version 撤销旧会话。姓名、昵称、角色、状态、密码哈希、createdAt 等字段保持原样。不调用账号创建逻辑、不生成新密码。
7. 若旧键和新键不同，仅在事务中再次确认旧键仍属于该 UID 后删除旧键；数字账号不改键。记录迁移操作者、目标 UID 和变更字段名称，不记录密码。事务失败不推进检查点；重跑时规范值及键已正确的记录可安全跳过。
8. 检查未完成 import_jobs，按共享规则重新校验并查重；不要直接清除原有错误或重置 offset/created 统计，更不能重复创建已处理行。发现冲突先人工解决。已完成导入记录作为历史凭证保留，不静默改写。
9. privacy_jobs 中的摘要不可反推原学号，不可盲目重算。维护工具同时兼容导入行的原始摘要和规范摘要；若需要更改某条摘要，必须有可信来源核对原值和 UID。不要因无法推算就覆盖或丢弃隐私清理记录。
10. 完成后验证每个非匿名账号恰有一个正确规范映射、所有 UID 与账号总数保持不变、数字账号映射不变、大小写登录一致且重复创建被拒绝。对照备份检查，确认无遗漏，再解除维护窗口。发生异常保持维护状态，用核准的备份和事务检查点恢复，不进行批量覆盖式回滚。

## Bootstrap 配置

私有初始化命令接受 `BOOTSTRAP_STUDENT_ID`（可含字母）、`BOOTSTRAP_NAME`、`BOOTSTRAP_PASSWORD`，以及可选 `BOOTSTRAP_NICKNAME`。昵称不设个人固定默认值；未提供时仍默认与姓名相同。真实密码只通过安全环境注入，不打印，不进入 Git，也不作为命令行参数。

本次没有执行 CloudBase 初始化或创建正式超级管理员；bootstrap 的字母学号及昵称仅在内存测试适配器中验证。
