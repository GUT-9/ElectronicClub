# 活动报名审核、多人负责人和可配置签到

## 本次修复

活动列表直接提供「报名审核与名单」「签到管理」，选择后自动加载，和活动设置分开展示，不再藏在长编辑表单底部等待手工查询。前台活动详情提供有权限成员的管理入口；个人中心的「我负责的活动」让只有单个活动授权的普通成员也能进入。只有报名审核或签到管理权限的角色可读取所需名单，导出仍单独校验导出权限；其他活动和全站成员资料不随此授权开放。

负责人选择显示姓名和角色，支持姓名/昵称/学号搜索、按角色筛选、分页多选、添加当前页，以及添加所选角色全部有效成员。最多100位（创建时包含创建者），多角色去重，超限明确报错而不静默截断。仅 `events.edit` 可调整负责人，普通活动负责人不能擅自给其他人增加管理权。角色批量添加保存的是当前名单，之后角色分配改变不会自动影响既有活动。已停用的原负责人保留历史关联，不能登录管理，保留他们不再阻止修改活动；不能新添加停用账号。

编辑保存会重新读取服务器并核对封面与负责人。活动 UID 和每个负责人关联保持一致；后台选择器只返回必要姓名、昵称、状态和角色，不返回手机、邮箱、学号或完整成员档案。旧按学号查询接口继续保留兼容。

签到码默认30分钟，可设置0.5–1440分钟（服务端30–86400秒），随活动保存，也可在签到管理直接修改。旧客户端显式传120秒仍有效。重新生成即作废旧码；结束签到、停用活动或关闭签到功能均作废现有码，重新启用不会恢复旧码。状态查询只返回开放状态和到期时间，不返回数据库中的摘要或旧明文码；刷新后如需分享，请生成新码。可复制签到码或签到链接，成员登录且报名通过后仍需本人确认签到。关闭报名但保留签到时，已通过成员仍可签到。

人工补签可直接从当前名单选择成员；名单外成员保留按学号查找。必须给出原因，拒绝停用成员和未发布活动。补签待审核记录会同时批准（原待审核名额已占用）；已取消/拒绝或未报名成员记为人工补签，不挤占普通报名名额。重复操作不会产生重复签到。

报名名单改为数据库分页，包含搜索、学院/班级、报名/签到状态筛选和筛选汇总；单页最多100，默认20。导出按数据库分页读取所选筛选结果，最多10000条，超过时提示继续筛选，不会静默少导数据。

## API

- GET `/api/events/manager-roles?page=1`：负责人选择所需角色名称分页，需events.edit。
- GET `/api/events/manager-options?search=&roleId=&page=1&pageSize=20`：有效成员必要信息分页，需events.edit。
- POST `/api/events/manager-options/resolve`：`uids`，回显所选负责人姓名/状态，需events.edit。
- POST `/api/events/manager-options/by-role`：`roleIds`，当前有效成员去重批量选择，需events.edit。
- GET `/api/events/:id/managers`：本活动负责人必要信息，需活动管理范围授权。
- GET `/api/events/:id/access`：当前成员在该活动的布尔能力，不返回他人权限或私人资料。
- GET `/api/events/:id/checkin-status`：开放状态/有效期/到期时间，需签到管理或本活动负责人。
- 原活动保存接口新增 `checkinTtlSeconds`，原POST签到码接口仍使用 `open`/可选 `ttlSeconds`。
- 原报名名单/审核/导出/签到/补签接口保留，写操作沿用Cookie、CSRF、服务端范围检查和事务审计。
