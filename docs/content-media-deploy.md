## 使用方式与清晰度

活动、新闻、帖子正文使用统一编辑器。将光标放在需要的位置，点击“插入图片”，选择 PNG/JPEG/WebP。压缩与上传完成后插入正文，可预览，并从图片列表直接移除。正文还支持安全的 Markdown 表格。HTML 和任意外部图片语法按普通文字显示，只有受控媒体引用会渲染成图片。

原图上限为 3MiB（3,145,728 字节），上传成品上限为 50KiB（51,200 字节）。每篇正文最多 12 张不同图片，另可有一张封面。浏览器验证文件签名、解码后重编码，去除原始元数据；保留最大 1600 像素长边，优先使用 WebP，并搜索预算内较高的编码质量，再按需缩小尺寸。图片不会放大。50KB 的固定上限不可能让任意复杂长图都保持原始细节；建议细密电路图分成数张局部图。

新封面及弹窗上传同样使用此流程。旧 HTTPS 封面、旧 Base64 封面和旧论坛附图继续显示。旧 `/api/forum/images` API 仍保留原有 32KiB 上传约定以兼容已部署客户端，新前端统一走媒体 API。

正文仅保存 `![说明](media:图片ID)`，封面仅保存 `media:图片ID`；不将图片 Base64 塞入活动、文章或帖子保存请求。新图片默认无文件名图注，避免公开本地文件名；修改方括号说明可添加图注。

## 图片 API 与网关限制

全部写接口沿用现有 Cookie 登录、CSRF 检查和事务机制。

- `POST /api/media`：`{mime,bytes}`，创建上传，返回 `id`、`chunkCount`。
- `POST /api/media/:id/chunks/:index`：`{data:Base64分片}`，index 为 0–2。每片最多 24KiB 原始字节，即 32KiB Base64；可在完成前重试同一分片。
- `POST /api/media/:id/complete`：`{}`，校验完整字节、真实格式、CRC/文件结构、尺寸及数量。JPEG/PNG/WebP 必须与声明一致，拒绝 SVG、可执行文本和不完整图片。
- `POST /api/media/:id/delete`：`{}`，仅上传者可以删除尚未被内容引用的图片。
- `GET /api/media/:id`：按真实 MIME 返回二进制，`nosniff`、`no-store`。公开内容的图片游客可读；草稿、待审核、隐藏、撤回内容不向游客暴露。公开读取不写会话，减少多图并发争用；私有预览仍鉴权。

每个浏览器分片请求与后端 SQL RPC 提交均受 64KiB 保守预算约束。50KiB 图片需最多三个分片，不能直接假设 Base64 JSON 小于网关限制。保存内容时事务内校验图片归属、完成状态、引用数量和内容权限；不能将他人私有图片绑定到自己的内容。弹窗管理员可复用其关联的已发布活动/文章封面。

每名成员每 10 分钟最多启动 24 次上传，最多保留 16 张未绑定图片，避免无限暂存；论坛发帖限制也会限制普通成员上传。计数、预算和引用通过原有事务及并发冲突重试维护。新旧图片共享现有 `FORUM_IMAGE_BUDGET_BYTES`（默认 32MiB 编码文本预算）和存储计数，不需要额外付费存储。该环境变量名称保留以兼容现有配置。

## 暂存清理与回滚

原私有 `forum-maintenance.js --cleanup-staged` 现在同时清理超过 24 小时且没有内容引用的通用图片，每批最多 50 张；重新在事务内确认引用为空，归还预算并记录审计。只在获授权的私有终端执行，没有开放 HTTP 清理接口。不要在生产重新运行 bootstrap。被软删除内容仍保留图片引用，便于恢复；如需释放空间，先通过合法编辑移除对应图片并保存，再执行暂存清理。

推荐出现问题时前滚修复。回滚前端/函数不要求删除新表；必须保留媒体表、分片、预算记录及 011 版本。老前端无法渲染新媒体引用，回滚前应评估已发布的新正文/封面，或只回滚有问题的界面改动并保留新媒体支持。不得直接 DROP 表或恢复整库备份覆盖当前业务。权限分组仅为显示元数据，可恢复旧名称而不改变任何人的权限；通常无需回滚标签。
